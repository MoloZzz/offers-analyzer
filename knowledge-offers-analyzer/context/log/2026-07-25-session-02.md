# Session log — 2026-07-25 (02)

## Goal

Production incident: every poll cycle failing. Diagnose and fix.

```
ERROR (37): Search failed for profile {"context":"PollService"}
  EntityMetadataNotFoundError: No metadata for "MonthlyBudgetState" was found.
    at RateBudgetService.getMonthlyBudgetState (rate-budget.service.ts:125)
    at RateBudgetService.tryConsume (rate-budget.service.ts:62)
    at AutoRiaSource.get → AutoRiaSource.search → PollService.runCycle
```

## Root cause

`MonthlyBudgetState` was never added to the `ENTITIES` array in
`src/common/database/data-source.ts`. That array is the **only** registration path — there is no
entity glob and no `autoLoadEntities` anywhere in the repo.

`SchedulingModule` *did* call `TypeOrmModule.forFeature([RateBudgetWindow, MonthlyBudgetState])`
and `RateBudgetService` *did* `@InjectRepository(MonthlyBudgetState)` — but `forFeature` only
registers a repository **provider token** and calls `dataSource.getRepository()` lazily. So the app
booted clean, DI resolved, all 33 unit suites (mock repos) stayed green, and the failure surfaced
only on the first real query. **Blast radius: total** — `tryConsume()` is on the path of every
source fetch, so no profile could be polled at all.

Commit `ddf72c9 feat: monthly_budget_states` touched the module, service, migration, config and
tests but not `data-source.ts`. Sibling entities from neighbouring commits (`DealOutcome`,
`ListingDisappearance`, `RateBudgetWindow`) were all registered — this one entity was the miss.
The DB table itself existed; migration `1785194400000-adr-0009-monthly-budget.ts` had created it.

Notably the project *knew* about this step — `specs/007-deal-outcomes/tasks.md:13` and
`specs/004-realized-price-calibration/tasks.md:12` both list "wire into ENTITIES" as an explicit
manual task. ADR-0009's spec omitted it. A checklist item that only works when someone remembers to
write it down is not a control; hence the test below.

## Fixes

1. **Registration** (`data-source.ts`) — import + `MonthlyBudgetState` in `ENTITIES`, placed next
   to `RateBudgetWindow` to keep the scheduling entities grouped. No schema change follows
   (`synchronize` is hard-coded `false`, table already migrated).
2. **Regression guard** (`test/unit/entities-registry.spec.ts`, new) — walks `src/**/*.entity.ts`,
   `require`s each so the decorators run, then asserts every class in TypeORM's
   `getMetadataArgsStorage().tables` is present in `ENTITIES`, failing with the missing class names.
   **Verified it actually fails**: removing the new line reproduced `+ "MonthlyBudgetState"`.
3. **`numeric` transformer** (`monthly-budget-state.entity.ts`) — `dailyBudget` was the only
   `numeric` column in the codebase missing `numericTransformer`, so it returned a *string* from
   `node-postgres` despite being typed `number`. That's why `rate-budget.service.ts:161` needed
   `Number(state.dailyBudget) || 0`; that workaround is now `state.dailyBudget ?? 0`. Transformers
   don't touch DDL and the migration already declares `numeric(10,2) NOT NULL DEFAULT 0`, so
   `migration:generate` stays churn-free.
